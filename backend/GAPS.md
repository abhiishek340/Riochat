# GAPS

Decisions taken where the specifications are silent, ambiguous or deliberately
leave a choice open. One line per decision. Format:
`- <area> | <question> | <decision>`

Append only. Feature engineers add their own lines under their area name.

## platform

- platform/config | The spec says a built-in development JWT secret and data-encryption key exist but not their values. | `DevJWTSecret` and `DevDataEncryptionKey` in `internal/platform/config/config.go` are fixed literals that start with `riochat-dev-`; production rejects them, other environments only warn.
- platform/config | The default PostgreSQL DSN omits the password. | Default DSN is `host=127.0.0.1 port=5432 user=riochat password=riochat dbname=riochat sslmode=disable TimeZone=Asia/Shanghai`.
- platform/config | YAML shape of list-valued keys (`cors_allow_origin`, `trusted_proxies`, `ssrf_allowed_*`) is unspecified. | Each accepts either a comma separated string or a YAML list; stored internally as a comma separated string.
- platform/config | `http_port` may be written as a number or a string in YAML. | Both are accepted; the value is kept as a string (an empty environment value must stay representable).
- platform/config | Branding and the dynamic overlay beyond token TTLs and rate limits are not needed by the foundation. | `Config.Dynamic` carries only `Auth` (token TTLs, rate-limit switch and RPMs). The settings area adds fields it needs and owns the `system_settings` overlay (see ARCHITECTURE.md, "Settings overlay").
- platform/config | Where do geoip, tracing and branding settings get consumed? | They are loaded and validated only; no consumer exists in the foundation. Their owning areas read them from `d.Config`.
- platform/cache | Sliding window and fixed window differ between Redis and memory in the spec ("tests must not depend on this"). | Both backends behave identically: the sliding window records only allowed attempts; the fixed window starts at the first hit and does not extend on later hits.
- platform/cache | Non-positive TTL on KV operations. | Treated as one minute on every operation and both backends.
- platform/cache | The spec lists many domain stores (settings cache, queues, generation streams, circuit breaker, OAuth hand-off). | The foundation provides only generic atomic primitives (`Get/Set/SetNX/GetDel/Delete/Incr`, two rate limiters). Domain stores are built by their owning areas on top of those primitives, using key prefixes named in their specs.
- platform/cache | Redis rate limiting uses client time. | The Lua scripts receive the client clock in milliseconds; skew between instances is accepted.
- platform/database | sqlite-vec, pgvector and vector-table migrations (spec 5.7), table comments, per-driver build tags (spec 4). | Not part of the foundation. Both drivers are always compiled. Vector storage belongs to the embedding/knowledge areas as migration steps using `migrate.Exec`.
- platform/database | SQLite driver choice. | `gorm.io/driver/sqlite` (cgo, mattn/go-sqlite3); DSN parameters use its `_busy_timeout/_foreign_keys/_journal_mode/_synchronous/_cache_size` names. Pragmas are also applied after open.
- platform/database | PostgreSQL code paths could not be exercised in the build environment (no server). | Covered by compile-time use only; the PostgreSQL-specific parts are the pool settings, `WithAdvisoryLock` and error translation (SQLSTATE 23505).
- platform/database | Statement logging. | Bound parameter values are never logged (a GORM `ParamsFilter` strips them); failures log at error, statements over 200 ms at warn, everything else at debug outside production.
- platform/database | Tracing spans for database/Redis/S3 and the OTLP exporter (spec 14.2). | Not implemented; trace IDs are taken from a valid inbound `X-Trace-ID` or generated.
- platform/migrate | Spec requires idempotent migrations on every start and no version table. | The runner executes every registered step on every start, schema phase of all areas first, then seed phase of all areas. A PostgreSQL advisory lock serializes concurrent instances.
- platform/migrate | Table naming rule (spec 5.4). | `migrate.AutoMigrate` rejects models without an explicit `TableName()` or with a table not starting with a permitted domain prefix.
- platform/logx | Exact timestamp and caller formats. | `time` is `2006-01-02T15:04:05.000Z07:00`; `caller` is `<dir>/<file>.go:<line>`; HTML characters are not escaped in JSON output.
- platform/httpx | Validation library and tag name. | `go-playground/validator` with the struct tag `binding:"..."`. Field names in messages come from Go field names (not JSON tags), converted per spec 10.5.
- platform/httpx | Behavior for an over-limit JSON body. | 413 with the generic `request.invalid` envelope. `BindJSON` caps bodies at 4 MiB; `BindJSONLimit` takes an explicit cap.
- platform/httpx | Field-name rendering of initialisms followed by a lowercase letter (for example `URLs`). | Only whole-word leading initialisms are lower-cased; otherwise just the first letter is lower-cased.
- platform/httpx | Status for a typed error returned without an explicit status. | `httpx.FailErr` uses the error's optional `Status` hint, else 500. `httpx.Fail(c, status, err)` is the explicit form.
- platform/middleware | Layout of the access log message. | Header line `[AccessLog] METHOD path` then one `Key: value` line each for Route, StartTime, EndTime, Latency, ClientIP, Response, RequestID, TraceID, UserID, UserAgent, then ErrorCode and Error when present.
- platform/middleware | A handler panic and the access log. | The access log emits the request as a 500 without persisting it; `Recovery` persists the error record (so each panic is recorded once).
- platform/middleware | `ErrorRecorder` calls. | Invoked synchronously after the response; implementations must be quick and hand slow work to a detached task.
- platform/middleware | CORS when the request has no `Origin`. | No `Access-Control-Allow-Origin` header is sent; the other CORS headers and `Vary: Origin` are.
- platform/middleware | Gzip for responses without a Content-Type. | Not compressed (only declared textual types qualify).
- platform/middleware | Authentication before any session validator is registered. | Tokens are accepted on signature, expiry and type alone, and a `session_validator_not_registered` warning is logged at startup. The auth area registers the validator through `Deps.Sessions`.
- platform/middleware | Rate limiting of unmatched routes. | The 404 fallback is outside the route groups and is not rate limited.
- platform/server | Reserved path prefixes for front-end hosting. | `/api`, `/swagger`, `/healthz`, `/readyz` match on a path-segment boundary (exact or followed by `/`), so `/apiary` is a front-end route.
- platform/server | Swagger UI route. | Not mounted by the foundation.
- platform/server | Readiness when the database is absent. | Reported as `db: not_configured` and counts as unhealthy, like a missing cache.
- app | Bootstrap administrator and the local `owner` user (spec 2.4-2.5), dynamic-settings overlay (3.5), content-moderation, embedding, icon-cleanup and rotation workers (15). | Not in the foundation. The owning areas register `Lifecycle.OnStart` hooks and workers; `Deps.LocalGrant` is where the auth area registers the desktop login grant issuer.
- app | Worker shutdown wait. | Workers get 10 s after cancellation; detached tasks get 5 s (spec 2.6).
- app | Local mode when no grant issuer is registered. | The ready line is still printed with an empty `grant`, and a warning is logged to stderr.

## errorlog

- errorlog | Spec says persistence is disabled "in automated tests" and in local sidecar mode; how does the new code know it is under test? | Only local mode (`Config.Local.Enabled`) disables persistence; there is no test switch, so area tests that mount the area do record. Areas that do not mount `errorlog` are unaffected because the recorder hook stays empty.
- errorlog | Where does the user's name come from, given tables are owned per area? | `UserDirectory` interface in the package; `Mount` uses a default that reads `id, username, display_name` from `identity_users` (rows with `deleted_at` set count as missing). The integrator may call `errorlog.MountWith(adapter)` to use the auth area's service instead.
- errorlog | The admin routes group is mounted at `/api/v1` with no `/admin` segment. | The handler registers `/admin/error-logs` on `Routes.Admin` so the final path is `/api/v1/admin/error-logs`.
- errorlog | The log-cleanup area must delete from `system_error_logs` but may not query foreign tables. | Exported `errorlog.PurgeBefore(ctx, db, before) (int64, error)` hard-deletes rows with `created_at < before` and returns the count.
- errorlog | The platform hands over cause text that may already carry a "...(truncated, N bytes total)" suffix. | The recorder redacts again and hard-cuts the cause at 4096 bytes on a character boundary, so the stored value never exceeds the limit (the suffix can be partly cut).
- errorlog | Timestamp storage and comparison across drivers. | Occurrence times are stored in UTC and range filters are converted to UTC before comparison; `created_from`/`created_to` accept RFC 3339 only (a raw `+` offset must be URL-encoded).
- errorlog | Keyword matching case folding. | The keyword and columns are lower-cased with SQL `LOWER` and Go `strings.ToLower`; `%`, `_` and `\` in the keyword are matched literally. SQLite's `LOWER` is ASCII-only, so non-ASCII case-insensitivity holds on PostgreSQL only.
- errorlog | Index names and the extra indexes. | Indexes are the GORM default names on `request_id`, `user_id`, `status_code`, `error_code`, `created_at`; no composite index is added.
- errorlog | Behavior for a `user_id` larger than 32 bits. | Treated as invalid (`invalid user_id`).
- audit | Where does the shared `POST /admin/logs/cleanup` endpoint live (it spans audit, auth, usage, orders, conversation, moderation, errors)? | Not mounted by the audit area, to avoid a duplicate route. The area exports `ValidateCleanup` (type/before checks in spec order, all seven types), `PurgeBefore` (hard delete, strictly older) and `Recorder.RecordCleanup` (the `admin_cleanup_logs` entry); the integrator or log-cleanup owner mounts the route once and calls them. A reference wiring is in `audit_test.go`. Mounted in `integration/log_cleanup.go` (from `MountAudit`): `auth.PurgeEventsBefore`, `billing.PurgeUsageBefore`/`PurgeOrdersBefore`, `conversation.PurgeEventsBefore` (run events), `errorlog.PurgeBefore`, `contentmoderation.Service.DeleteEventsBefore` and `audit.PurgeBefore` serve the seven types.
- audit | The list endpoint needs display name and username of actors but the user tables belong to another area. | The area defines `ActorResolver` and `SetActorResolver`; the user area (or an integrator adapter) registers it. Without one, actor name and label fields are empty strings.
- audit | How do other areas obtain the shared recorder? | `audit.NewRecorder(db, logger, clock)` returns a nil-safe `*Recorder` (`Record`, `RecordRequest`); the integrator creates one at startup and hands it to the areas. A nil recorder records nothing, matching "auditing not configured".
- audit | Detail value that serializes to JSON `null` (nil pointer, nil map). | Stored as `{}`, same as an absent detail, so the column is always a JSON object or array.
- audit | Detail JSON escaping of `<`, `>`, `&`. | Not escaped (compact JSON, characters kept literal) so keyword search on the stored text finds them.
- audit | Over-long values (request id 64, action/resource/resource id 128, ip 64, user agent 255). | Trimmed then truncated on a UTF-8 boundary before insert, never failing the write; spec only states resource id and user agent explicitly.
- audit | Insert uses the request context? | The insert runs on a detached context with a 5 second timeout so a canceled request does not lose the record; it is synchronous so ordering by id reflects call order.
- audit | Timestamps and range filters. | Rows are stamped with the injected clock in UTC; `created_from`/`created_to` are converted to UTC before comparison, so offsets in the query denote the same instant.
- audit | `actor_user_id` upper bound. | Parsed as a signed 64-bit integer; zero, negative, non-numeric, decimal or overflowing values give 400 `invalid actor_user_id`. Leading/trailing spaces in query values are trimmed.
- audit | Extra index on `created_at`. | Added (`idx_audit_logs_created_at`) for the time-range and time-ordered listings; exact original index names are unknown and not part of the contract.
- audit | Sensitive-value redaction helper. | `audit.RedactValue(value, sensitive)` and `audit.Redacted` are exported for the settings area; classification of which settings are sensitive stays with that area.
- audit | Catalogue actions (spec 6) and scenarios 18-21 (settings redaction, export, moderation views, client metadata). | Emitted by the owning areas through the recorder; client metadata capture already exists in `platform/middleware` (`AuditFromRequest`). Not testable inside this area.
- announcement | Index and constraint names are not specified. | Own names: `idx_system_announcements_listing` (pinned, priority, updated_at, id), `idx_announcement_user_states_version` (unique on announcement_id, user_id, announcement_updated_at), `idx_announcement_user_states_dismissed` and `idx_announcement_user_states_closed` (partial, WHERE the second column IS NOT NULL); single-column indexes use GORM's default names.
- announcement | Storage precision of the version (`updated_at`) is only said to need a lossless round trip. | Every write truncates version and window instants to microseconds and stores UTC, so PostgreSQL and SQLite behave the same and the client's echoed `updatedAt` matches by instant (`Equal`), in any offset. Rows from older databases with finer precision are served as stored and still match when echoed back.
- announcement | Two edits within one clock tick (or with a frozen test clock) would give the same version. | An edit that writes always produces a version strictly greater than the previous one (previous + 1 microsecond when the clock has not advanced).
- announcement | How concurrent edits to one row are serialized on both SQLite and PostgreSQL. | Each edit, dismiss and close first runs a no-op write (`UPDATE ... SET id = id`) on the row inside its transaction, which takes the row lock on both drivers and doubles as the existence check.
- announcement | Display-window filtering of the user list. | Done in Go over the `status = 'active'` rows, so the comparison does not depend on how a driver orders timestamp text; the user list is not paginated by contract.
- announcement | Case-insensitive keyword search. | `LOWER(col) LIKE %kw%` with `%`, `_` and `\` in the keyword escaped; SQLite lowercases ASCII letters only, so non-ASCII case folding is exact only on PostgreSQL.
- announcement | Response status of create. | 200 with `{announcement}` as the spec says (not 201).
- announcement | Over-limit lengths. | Counted in characters (runes) at the request layer (`request.invalid_body`); the post-trim check also counts characters and can only fail for blank text, so multi-byte text up to the documented maxima is accepted.
- announcement | Invalid `startsAt`/`expiresAt` on create (empty string, non-RFC 3339) or a non-string value on patch. | `request.invalid_body` 400; only the PATCH body treats null, empty and whitespace-only strings as "clear".
- announcement | Path ids above the signed 64-bit range or with a sign/decimal/exponent. | `announcement.invalid_id` 400 (the id must be a plain positive base-10 integer that fits a signed 64-bit column).
- announcement | Year-1 timestamp written with a non-UTC offset in dismiss/close. | Treated like the zero value: 400 `request.invalid_body` naming `updatedAt`.
- announcement | Order of checks on dismiss/close. | Path id first, then body, then eligibility (not-found); a missing announcement with a bad body answers 400.
- announcement | `include_dismissed` surrounding whitespace. | Trimmed before parsing; other spellings than the twelve listed mean false.
- announcement | Capability off for the user list. | The route is registered outside the gate and checks the flag per request, answering 200 with `[]` (`data` is an empty array, never null).

## memory

- memory | Vector storage: the spec names a SQLite vec0 table and an optional pgvector column, neither of which the build provides. | Vectors live in a plain companion table `user_memory_embeddings` (memory_id, user_id, embedding_signature, embedding packed as little-endian float32) on both databases; search loads the caller's embedded entries under the signature and ranks by exact cosine in Go (bounded by the 500-entry cap). The table has a different name from the spec's vec0 table so an existing virtual table is never touched; old vectors are ignored and entries re-embed on their next write. No `embedding` column is added to `user_memories`.
- memory | Whitespace-only key or value on PUT (spec allows rejecting). | Rejected with 400 `request.invalid_body` after trimming, nothing stored; `Service.Upsert` also refuses an empty or over-128-character key with `ErrInvalidInput`.
- memory | Soft vs hard delete on DELETE. | DELETE soft-deletes the row (the table has `deleted_at`) and removes its vector; account purge (`Service.PurgeUser`/`PurgeUserTx`) hard-deletes everything including soft-deleted rows.
- memory | Uniqueness over live rows only. | Partial unique index `uidx_user_memories_user_key_live` on (user_id, memory_key) WHERE deleted_at IS NULL, created by a migration step on both dialects; a concurrent duplicate create is retried once as an update.
- memory | No embedding provider package exists yet. | The package defines the `Embedder` interface (Enabled, Embed returning vector and signature); the integrator injects one with `memory.MountWith(d, memory.Options{Embedder: ...})`, which also returns the `*Service` for chat and account deletion. Plain `Mount` runs without an embedder.
- memory | Audit writer wiring. | `MountWith` builds `audit.NewRecorder(d.DB, d.Logger, d.Clock)` from the audit area's exported recorder; the audit area's migrations must be registered for rows to persist (failures are logged and swallowed).
- memory | Chat integration is outside this area, but section 8 prescribes its inputs. | Provided as exported helpers: `Service.ListCached` (3 minute per-user cache with a one-minute sweep worker, invalidated by every write), `SelectRelevant`, `KeywordSelect`, `FormatPrefs` (400 token budget), `FormatMems`, `PromptStateSignature`, `Artifacts` and `BuildPromptContext`. Token estimates default to `DefaultEstimate` (about 4 ASCII bytes or 1 non-ASCII character per token); chat may pass its own estimator.
- memory | Prefs budget accounting. | The `# prefs` heading counts toward the 400 tokens; lines are added in list order and the first line that would exceed the budget ends the block (later shorter lines are not skipped); when no line fits, no block is produced.
- memory | Artifact excerpt size and the link between prompt source references and artifacts. | Excerpt is the first 600 characters of the value; `SourceRef{ID: key, Label: scope}` is returned in the same order as the artifacts so chat can link them by index.
- memory | Audit detail for DELETE and PUT key. | DELETE passes no detail (the audit writer stores `{}`); PUT passes the key as received and the audit writer itself trims surrounding whitespace when storing.
- memory | Over-long `updatedBy` or `scope` from non-HTTP callers. | Truncated to the column size (32 characters) instead of failing the write.
- memory | Semantic recall deadline. | The 200 ms limit is a context deadline passed to `Embedder.Embed` and also enforced by the caller (the call runs in a goroutine and is abandoned at the deadline), so an embedder that ignores its context cannot delay chat.

## knowledgebase

- knowledgebase | Counts, sorting by file count and the RAG-ready resolution need columns of `file_objects`, a table owned by the file area. | The area reads `file_objects` (and only reads it) through its own minimal `fileObject` model and joins; it never migrates or writes that table. The file area must keep the columns named in the spec.
- knowledgebase | Where do the feature switch (`knowledgebase.enabled`) and the upload cap (`storage.max_upload_file_bytes`) come from while the settings area has no exported API? | A `Settings` port; the default reads the `system_settings` row directly and falls back to enabled and 20 MiB when the table, row or value is missing or unparsable. The integrator may supply the settings area's reader through `MountWith`.
- knowledgebase | How does the area reach file content, safe file deletion, the upload pipeline and the embedding queue owned by other areas? | Ports (`FileReader`, `FileCleaner`, `FileUploader`, `Embedder`, `Vectorizer`) passed to `MountWith`/`NewService`. A nil member means unavailable: content 500 `knowledge_base.internal`, delete with files 503 `knowledge_base.file_cleanup_unavailable`, upload 400 `knowledge_base.invalid`, embeddings 503 `embedding.service_not_configured`, `canVectorize` false with an empty reason.
- knowledgebase | Audit writing without a dependency on the audit area. | An `Auditor` port receiving actor, request id, client IP, user agent, action, resource `knowledge_bases`, resource id and detail map; the default only logs. Auditing is best effort and never fails a request.
- knowledgebase | Which key identifies a base in `chat_conversation_project_knowledge_bases` (the spec says uint, the conversation area stores a string up to 64 characters)? | Deleting a base (and purging a user) removes rows whose `knowledge_base_id` equals the base's public id or its decimal numeric id; the step is skipped when the table does not exist yet.
- knowledgebase | The "shared file-processing predicate" behind the `processing` flag is not specified. | `processing` is true under the same rule as `processingFileCount`: processing_status in {uploaded, queued, extracting, embedding}, or extract_status or embed_status equal to `processing`.
- knowledgebase | Patch of a personal base carrying `sortOrder` (the spec only names `enabled`). | Both `enabled` and `sortOrder` are refused with 400 `knowledge_base.invalid`, since the body accepts only name and description.
- knowledgebase | Adding or removing files: is `updated_by_user_id` changed? | Only `revision` and `updated_at` change; `updated_by_user_id` stays.
- knowledgebase | `enabled=false` on create must override the column default `true`. | The row is inserted and then `enabled` is written explicitly inside the same transaction.
- knowledgebase | Case-insensitive keyword and name sort use SQL `LOWER`, which is ASCII-only on SQLite. | Accepted; PostgreSQL folds Unicode. The keyword is lower-cased in Go before matching, and `%`, `_` and `\` in it are matched literally.
- knowledgebase | Error code for a missing platform pool file on `GET /admin/knowledge-bases/files/:file_id/content`. | 404 `file.not_found` (the spec only says 404); the pool check happens before the reader is called.
- knowledgebase | Embedding submission with blanks or duplicate ids (spec gives only the 1..100 and 1..64 bounds). | Ids are trimmed and de-duplicated silently; all-blank is 400 `knowledge_base.invalid`; the audit `requested_file_ids` lists the normalized ids.
- knowledgebase | Order of the statuses array and of ties in file lists. | Statuses follow the link sort order then file id; file lists order by link sort order, time added, then file id.
- knowledgebase | Snapshot with no body at all. | Treated like `{}`.
- knowledgebase | Upload body that is not multipart, a malformed multipart stream, and unknown uploader errors. | Not multipart or no `file` part: 400 `file.required`; malformed stream or unopenable part: 400 `file.invalid_stream`; body over the cap: 413 `file.too_large`; any other uploader error: 500 `knowledge_base.internal`. The stored file name is the base name of the client's file name.
- knowledgebase | Messages for codes the spec lists without text (`file.required`, `file.invalid_stream`, `request.invalid_file`, `file.embedding_unavailable`, `knowledge_base.invalid_reference`, `.not_ready`, `.unavailable`). | "file is required", "invalid file stream", "invalid file", "embedding is unavailable for this file", and the conversation area's texts for the three conversation codes.
- knowledgebase | Platform file delete: a file still linked to any base. | Refused by this area itself with 409 `knowledge_base.platform_file_in_use` before the cleaner is called, in addition to whatever the file subsystem reports. Blank id (400) is checked before the missing cleaner (503).
- knowledgebase | Available-files: should the file purpose be filtered? | No; any active, non-deleted file of the proper owner that is not already in the base is offered.
- knowledgebase | The feature switch is read on every user request. | No caching; the settings port is expected to be cheap.
- knowledgebase | Names of database indexes are not in the spec. | GORM naming is used (`idx_knowledge_bases_*`, `ux_knowledge_bases_scope_owner_name`, `idx_knowledge_base_files_base_sort`).
- knowledgebase | How other areas call into this one (conversation, account deletion, file deletion, retrieval, projects). | Exported `Service` methods: `Resolve`, `ValidateKnowledgeBases` (matches the conversation `Capabilities` signature), `FilterProjectBases`, `IsFileLinked`, `FileInEnabledBuiltinBase`, `CheckAccountDeletion`, `PurgeUserData(ctx, tx, userID)`, `Enabled`; the integrator builds the service with `NewService` and mounts it with `MountService`.

## contentmoderation

- contentmoderation | The feature needs conversation runs/messages, files, object storage, audit, user lookup and stream notification, which other areas own. | Small interfaces in `ports.go` (`RunStore`, `FileStore`, `ObjectStore`, `AuditWriter`, `UserDirectory`, `Notifier`); `Mount` uses none of them (events and stats still work, block application and image isolation are skipped), the integrator calls `MountWith(d, Ports{...})` instead and chat code calls `Shared().BeginRun`.
- contentmoderation | The spec's OpenAI-compatible HTTP client and the outbound SSRF policy are not in the platform. | The client lives inside the area (`provider.go`, `outbound.go`) with a replaceable `Provider`/`Doer`; the integrator may inject a platform outbound transport through `Ports.HTTP`.
- contentmoderation | Columns this feature owns on the run, message and file tables (`moderation_state`, `moderation_event_id`, `moderation_categories_json`, status `moderation_blocked`). | Declared and migrated by the owners of those tables; this area only reaches them through `RunStore`/`FileStore`.
- contentmoderation | The `system_settings` table is owned by the settings area but the area runs alone in tests. | The area declares a minimal `settingRow` (same unique index name as the channel area) and touches only namespace `content_moderation`.
- contentmoderation | Which view of `system_settings` updates should happen in one atomic upsert across drivers. | All nine keys are written in a single transaction with per-key upsert.
- contentmoderation | Stats window: "to" earlier than the clamped "from" when both are in the distant past. | Clamp `from` to now-90d first, then reject `to` earlier than the clamped value with 400 `request.invalid_query`.
- contentmoderation | Spec leaves `/events` `query` matching of the numeric user id and case folding open. | Raw value and its lowercase form are compared with `=` on event columns; users are matched case-insensitively through `UserDirectory.Search`; a positive numeric value also matches `user_id`.
- contentmoderation | Batch size and pass limit for content cleanup are free. | 100 events per batch, at most 20 passes per run; a pass that clears nothing stops the run.
- contentmoderation | Object key for isolated images is not fixed. | `content-moderation/<event public id>/<index>-<random suffix>` stored in `storagePath` of the image metadata, content type `application/octet-stream`.
- contentmoderation | Capability flag when the platform has no `contentModeration` flag. | Routes are mounted with `d.Gated(capability.ContentModeration)`, so the platform answers 404 `feature.disabled`.

## mcp

- mcp | Spec lists no `deleted_at` on `mcp_servers`/`mcp_tools`. | Both tables use `database.HardModel` (id, created_at, updated_at only); deletes are physical.
- mcp | HTTP status of `mcp.image_processing_failed` and `message.multiple_image_processors` is "see 9.4" and 9.4 only says 400 for the latter. | Multiple processors answers 400; image processing failure answers 502 (it is an upstream failure) with the public text from the spec.
- mcp | Runtime settings (`mcp_enable`, timeouts, limits, prompt) live in the settings area, which does not exist for this area yet. | `Settings` port (`MCPSettings(ctx) RuntimeSettings`); default is a static feature-off snapshot, the integrator wires the settings area via `MountService(d, Ports{...})`. Values are normalized at use (timeout 0 -> 10 s and cap 1800, concurrency 0 -> 8, selection limit clamped to [1,128] with 32 for non-positive, LLM rounds < 2 -> 5, tool calls <= 0 -> 8).
- mcp | `/mcp/tools` when the master switch is off. | 200 with an empty `results` array, before touching the database.
- mcp | Billing mode source (`self` or not) belongs to the billing area. | `BillingModes` port; when it is nil the stored prices are returned, when it errors the endpoint answers the generic 500.
- mcp | Project-default tool association rows belong to the conversation area. | `ProjectLinks` port; the default implementation deletes from `chat_conversation_project_mcp_tools` inside the caller's transaction and is a no-op when that table does not exist yet.
- mcp | Signing secret location. | Read per call from `Config.Security.MCPUserContextSecret` (env `MCP_USER_CONTEXT_SECRET` wins over YAML, resolved by the platform config); blank refuses the call with a signing error and sends nothing.
- mcp | Not-found target on update/sync/delete/reorder. | Surfaces as the generic 500, as the spec observes (no 404).
- mcp | Chat-time entry points for the conversation area. | `Service.ValidateSelection`, `ValidateToolDefaults`/`ValidateMCPTools`, `ResolveRunTools` returning a `RunTools` (`Tools`, `Guidance`, `Call`, `Usage`, `Fatal`, `Processor`), `ReencryptTokens` for the rotation job. Persisting tool-call rows and billing stay with the caller, which receives a `CallOutcome` and `UsageItem` list.
- mcp | Duplicate-call detection key. | Remote tool name plus the normalized (key-sorted, re-serialized) argument JSON.
- mcp | Server creation atomicity on SQLite vs PostgreSQL. | Count, max sort order and insert run in one transaction under `database.WithAdvisoryLock` (a no-op on SQLite, a PostgreSQL advisory lock otherwise).

## platform-llm

- platform-llm/layout | Where does the outbound/provider layer live and how is it registered? | Code is in `internal/features/platform-llm` (package `platformllm`, sub-packages `llm`, `outbound`, `objectstore`, `embedding`, `extract`, `mediadl`, `jobs`, `trace`, `textutil`). It owns no tables and no routes; `Migrations()` returns nil. Suggested registry line: `{Name: "platform_llm", Migrations: platformllm.Migrations, Mount: platformllm.Mount}` (area names cannot contain a hyphen). `Mount` publishes the built `*Platform` through `platformllm.Current()` and flushes tracing on stop.
- platform-llm/layout | Areas need the clients but `deps.Deps` has no field for them. | Areas call `platformllm.Current()` after `Mount` (or build their own with `platformllm.New`). The only process-level state is that one atomic pointer; everything else is injected.
- platform-llm/outbound | With enforcement off, are metadata and link-local addresses still refused? | No. Enforcement off means URL syntax checks only (scheme http/https, host present, no user info), as the spec states; the "always forbidden" list applies whenever enforcement is on, even against allowlists.
- platform-llm/outbound | Allowlist host entries must be "lowercase DNS names". | Entries are trimmed and lower-cased before validation, so `Example.COM` is accepted as `example.com`; IPs, ports, paths and the metadata host are rejected.
- platform-llm/outbound | Numeric host forms (`127.1`, `0x7f000001`, `2130706433`) are specified as rejected only for proxied requests. | They are rejected whenever enforcement is on, proxied or not: no legitimate DNS name looks like that, and lenient resolvers differ.
- platform-llm/outbound | Dialing a proxy address under enforcement. | The proxy's own host:port is remembered when the proxy function selects it and is exempt from address checks; the destination is validated textually and, for names, by one local resolution (resolution failure lets the request proceed).
- platform-llm/outbound | Pool key variants. | The key is origin plus kind (trusted, user-supplied, strict), connect timeout, redirect mode and integration name. Strict clients without a configured endpoint share one `*` origin slot.
- platform-llm/outbound | Credentials on cross-origin redirects. | Besides Go's own `Authorization`/`Cookie` stripping, `X-Api-Key`, `X-Goog-Api-Key`, `Api-Key` and `Proxy-Authorization` are removed on cross-origin hops.
- platform-llm/objectstore | S3 without the AWS SDK (no dependency may be added). | Requests are signed with a hand-written SigV4 (verified against the published documentation vector), payload hash `UNSIGNED-PAYLOAD`; unknown-size uploads are spooled to a temp file to obtain a content length. The "default AWS credential chain" is limited to `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`; with no credentials at all requests are sent unsigned. Region `auto` signs as `us-east-1`.
- platform-llm/objectstore | Local `Put` with a declared size that differs from the bytes written. | The declared size is advisory; the returned size is the number of bytes written.
- platform-llm/llm | Meaning of "endpoint kind" and "official protocol". | `Route.EndpointKind` is carried for callers only. "Official" behaviors (instructions field, verbosity, background, previous_response_id, prompt cache key) are tied to the `openai_responses` protocol itself.
- platform-llm/llm | Legacy protocol aliases (`openai`, `claude`, `grok`, `gemini`, ...) in `NormalizeProtocol`. | Accepted and mapped to the canonical protocol (the spec lists them for the option-policy key and says names "also usable as aliases when normalizing").
- platform-llm/llm | Message text when both `Content` and `Parts` are set. | `Parts` are authoritative; `Content` is prepended only when no part is a text part. File (extracted text) parts render as `File: <name>\n<text>`; audio/video parts are dropped by protocols that cannot carry them.
- platform-llm/llm | Where do the instructions go on protocols with no `instructions` field? | They become a leading system message (and join the merge of leading system messages); `developer` messages are treated as `system` on chat protocols.
- platform-llm/llm | `web_search` option on protocols without a spec-defined native tool shape. | Responses protocols add `{"type":"web_search"}`; OpenAI chat adds `web_search_options: {}`; OpenRouter chat adds `plugins:[{"id":"web"}]`; Anthropic `web_search_20250305`; Google/Interactions `google_search`.
- platform-llm/llm | `prompt_cache_options` explicit mode wire form. | Only the per-block `prompt_cache_breakpoint` markers are sent; the option itself is interpreted, not forwarded. Honored only on `openai_responses` and `openai_chat_completions`, never when ephemeral.
- platform-llm/llm | OpenRouter Responses synthetic ids. | `msg_riochat_<message index>` for assistant items, `fc_<callid>`, `fc_output_<callid>`, ids sanitized to letters, digits, `-`, `_`; the index counts positions after leading-system merging.
- platform-llm/llm | Custom (free-text) tool calls on Responses/Chat. | Arguments are normalized to the JSON object `{"input":"<text>"}` so every tool call carries JSON arguments.
- platform-llm/llm | Anthropic text blocks "concatenated (trimmed per block)". | Blocks are concatenated verbatim and the whole text is trimmed once (per-block trimming would glue words split by citations).
- platform-llm/llm | Anthropic thinking budget above `max_tokens`. | A supplied budget at or above `max_tokens` is clamped to `max_tokens-1`; a lone `budget_tokens` of at least 1024 without any enable flag enables thinking.
- platform-llm/llm | Gemini Interactions streaming and long-running video wire details are thin in the spec. | Parsing is tolerant (`outputs`, `steps`, `interaction` wrapper, `content.delta`/`interaction.complete` events); a buffered result whose status is still running is polled with GET `/v1beta/interactions/{id}` every 2 s until it finishes.
- platform-llm/llm | OpenRouter images wire shape beyond the request body. | Responses and SSE events are parsed with the OpenAI image parser (`data[]`, `*.partial_image`, `*.completed`).
- platform-llm/llm | xAI video request details not in the spec (extension source field, resolution tokens). | Extension sends `video:{url:<data URL>}`; resolutions matching `480p|720p|1080p` pass; polling stops after 1800 polls; statuses `failed`, `error` and `expired` are failures.
- platform-llm/llm | Buffered image-stream fallback and usage events. | When an image protocol streams but the upstream answers with JSON, exactly one usage event is emitted even if the body has no usage.
- platform-llm/llm | MCP client (13.3). | Not part of this layer; the MCP area owns its client. The opaque-payload sanitizer, tool-result preview (`textutil.PresentToolResult`), token estimate, chunking and signatures are in `textutil`.
- platform-llm/llm | Circuit breaker, rate-limit backoff and key rotation state (spec 6.10). | Not implemented here; they belong to the channel (routing) area on top of the cache primitives. This layer only exposes `llm.Retryable` and `llm.IsAccepted` for routing decisions.
- platform-llm/llm | Native tool catalog and option allow/deny policy. | Provided as pure helpers (`llm.Catalog`, `llm.MatchNativeTool`, `llm.FilterOptions` with the spec defaults) for the settings/channel/conversation areas to call; nothing reads the settings tables here.
- platform-llm/embedding | `{base}` handling. | OpenAI, Voyage and Jina use the base verbatim (`{base}/embeddings`); Gemini inserts `v1beta` when the base has no version segment and defaults to the public Google host.
- platform-llm/extract | Built-in PDF text and legacy `.xls` parsing. | No pure-Go PDF/BIFF parser is available without a new dependency: the built-in engine answers `builtin_unsupported` for them and callers select Tika/Docling/MinerU/OCR. `.docx`, `.xlsx`, `.csv`, plain text and (through antiword/textutil) `.doc` work.
- platform-llm/extract | PDF page renderer for model OCR. | `pdftoppm` (poppler) is the default renderer behind the `PageRenderer` port; missing tool means every page reports a render failure.
- platform-llm/extract | Tencent and Aliyun OCR. | Selecting either yields an `ocr_unavailable` engine, as the spec says there is no client.
- platform-llm/trace | OTLP over gRPC (default protocol). | gRPC needs generated protobuf stubs and an HTTP/2 client library that are not dependencies of this module. Spans are always exported as OTLP/HTTP JSON; with protocol `grpc` a warning `otel_grpc_exporter_unavailable` is logged and the endpoint must be the HTTP collector endpoint (default path `/v1/traces`).
- platform-llm/trace | Spans for inbound HTTP, database and Redis (spec 14.2). | Not created here (those layers are platform-owned); this package provides the tracer, W3C propagation, the outbound HTTP transport spans and S3 spans.
- platform-llm/jobs | Which workers are started. | Only the runner, queues, batch loop and retry helpers exist here; each feature area registers its own workers (reconciliation, file processing, moderation, icon cleanup, key rotation) with `Platform.Jobs`.
- platform-llm/textutil | Details of the tool-result preview not fixed by spec 12.4. | Top-level `answer`/`summary`/`message` text wins, then the first `{type:text,text}` object, then the first narrative-looking string (8+ characters, letters, a space or CJK, not a bare URL or opaque). A source is any object holding one of the URL keys; its title comes from `title`/`name`/`source`/`site_name`/`displayName` and its snippet from `snippet`/`description`/`summary`/`excerpt`/`content`/`text`. Embedded JSON documents are only extracted when they start a line (not fenced, not indented 4+).
- platform-llm/trace | Unsupported exporter protocol. | Any protocol other than empty, `grpc`, `http`, `http/protobuf`, `http/json` fails with "unsupported otel exporter protocol" when tracing is enabled; a disabled tracer ignores the value.
- platform-llm/geoip | Where GeoIP (spec 13.7) lives and how the auth area gets it. | New package `geoip` builds a `Resolver` (nil when disabled); `Platform.GeoIP` carries it. `geoip.Location` has exactly the field list of the auth area's `GeoInfo`, so the integrator converts with `auth.GeoInfo(loc)`. Ineligible addresses (private, loopback, link-local, multicast, unspecified) answer `ErrSkipped`.
- platform-llm/geoip | Source string for the `mmdb` provider and the MaxMind reader. | `geoip_api` for HTTP providers and `geoip_mmdb` for the database (accuracy `ip` for both). Localized names pick the configured languages (default `en`), then the first language alphabetically. Downloads go through the strict outbound policy, are verified by opening them, and replace the file atomically; failure backoff doubles from 1 minute to 1 hour.
- platform-llm/dockerx | Behavior when the docker binary is absent (spec 13.10). | The call fails with the text `docker_unavailable` before any process starts; a cancelled parent context returns the context error rather than `docker_timeout`.

## moderation-ports

- moderation-ports/objectstore | Where does the object-store contract live, given areas never import each other and `internal/platform` is not editable by areas? | New library package `internal/features/objectstore` (no routes, no tables, so it is not in `registry`): `Store` (Write, Open, Delete, Materialize), `NormalizeKey`, `Local`, `S3`, and `Manager`, which implements `Store` over the live `config.Storage` snapshot and rebuilds the backend whenever any storage setting changes. The integrator builds one `Manager` per hub (`Hub.objectManager`) and hands thin adapters to the areas that store bytes.
- moderation-ports/objectstore | The S3 backend cannot use an SDK (no new dependencies). | A small Signature V4 client over `net/http` (path-style or virtual-host addressing, `UNSIGNED` payloads are not used: uploads are spooled to a temp file to get the exact length and SHA-256). Ambient credentials mean the `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` environment variables only (no profile or instance-metadata chain); blank region means `auto`. Error bodies are never kept, only the S3 error code. Tracing spans and the "S3 compiled out" build error are not implemented (no build tags exist).
- moderation-ports/objectstore | Key rules beyond the spec text. | After the documented normalization, any `..` segment or a drive-letter prefix is `ErrInvalidKey`; a leading slash is simply trimmed, so `/etc/x` is the key `etc/x`. Local `Delete` of an invalid key succeeds silently; S3 `Delete` of an empty key succeeds, of a traversal key reports `ErrInvalidKey`.
- moderation-ports/chat-files | Should chat-file bytes move to the spec 5.4 key shape (`<owner public id>/<yyyy>/<mm>/<file id>_<name>`) and the staged-upload pipeline? | No. The stored `storage_path` stays `<user id>/<file id>`; the new `Ports.Objects` (`ObjectBytes`) stores it under the key `chat-files/<storage_path>`, which is the same place the built-in local writer used, so both modes see the same data. Without `Objects` the area keeps writing to `Storage.Local.RootDir/chat-files` (and still refuses a non-local backend). The integrator always passes the shared store, so S3 works for chat files.
- moderation-ports/chat-files | Upload de-duplication (5.5 step 4 and 5). | A per-process keyed gate serializes identical uploads (user, hash, size); an existing active record is reused only after its object is read back with the same size and SHA-256, otherwise the stale record is removed (attachments marked deleted, quota released, object deleted) and the search repeats (at most four rounds). A storage error while verifying is returned, never treated as "stale". Reuse also updates `last_accessed_at`.
- moderation-ports/chat-files | Object deletes of removed files. | `removeBytes` runs on a detached 10-second budget and only logs a failure; `Files.RemoveStored` (account deletion) reports failed paths as before.
- moderation-ports/bridge | How does the moderation engine reach runs, messages, files and streams owned by the conversation area? | `conversation.ModerationBridge` (handed out by `Ports.OnModeration`) speaks only primitives: `SetRunState`, `ApplyBlock`, `StaleRuns`, `LoadFile`, `RevokeFile`, `DeleteFileObjects`, `RetryBlockedDeletes`, `Emit`, `DiscardRetained`. `internal/integration/moderation_ports.go` adapts it to the engine's `RunStore`, `FileStore`, `Notifier` and the object store to `ObjectStore`; all adapters resolve the bridge lazily, so mount order does not matter.
- moderation-ports/bridge | `ApplyBlock` details the spec leaves open. | Messages are found by `run_id` (assistant always, user only for input direction); both get error code `content_moderation.blocked` and text `content blocked by moderation`; the run's `ended_at` is set when it was empty; the conversation's `updated_at` is bumped; trace rows (`trace_block`, `trace_event`) are deleted physically while tool-call rows stay. A missing run row fails the transaction. Withdrawn generated files release the owner's storage quota (they no longer count as theirs); the spec is silent on quota.
- moderation-ports/bridge | Loading images for a check. | `LoadFile` takes the internal file row id of an active file; the type decision uses the detected MIME falling back to the declared one and answers `ErrNotImage` (a silent skip in the engine, new sentinel `contentmoderation.ErrNotImage`) before any bytes are read; records larger than 20 MiB answer a failure without reading. Withdrawn or missing rows are `ErrFileNotFound`. The caller owns the authorization: only ids of the turn's own files are passed.
- moderation-ports/bridge | Stale-run listing and on-demand recovery. | `StaleRuns` returns at most 100 runs in `pending`/`moderating` with `updated_at` older than the cutoff, with the assistant message ids. The on-demand "read state, ignore unless pending or moderating" variant is not added: the periodic pass is the only caller, as in the spec's shipped behavior.
- moderation-ports/notifier | When does the engine's `moderation_blocked` reach the client? | While the run's own job is tracking the turn, the bridge holds the engine's blocked event (`liveRun.holdBlocked`) and the job publishes the terminal event itself after persisting billing, so the one terminal event carries `data` (the final result) and `billedReason`. `moderation_checking` goes out immediately. Late and recovery blocks are published only when the run is still live in this process; otherwise they are dropped (reload shows the blocked state). `DiscardRetained` removes buffered `delta`, `upstream_think_delta`, `media`, `media_delta` and `thinking` events and resets the snapshot text; the cache copies of the dropped events are deleted.
- moderation-ports/conversation | How does a persisted turn use the engine? | `Ports.Moderation` may also implement `SessionModeration` (`Begin` returns a `ModerationSession`). The send job then queues the input text and all attached files (the source video of a video extension excluded) while the model runs, cancels generation through the session's callback on an input hit, and always calls `Finish` once after generation (also for a failed or cancelled one, with the partial reply), so a run never stays `pending`. A blocked verdict goes through `finishBlocked`, which is idempotent over rows the engine already withdrew. Moderation implementations without `Begin` keep the old text-only `Check` flow. Regenerations (reused user message) do not re-check the input.
- moderation-ports/conversation | Live billing label. | `billedReason` is set on the stream only for output-direction blocks of a paid reservation (mode other than `self`); for input-direction blocks it is added to the stored pricing snapshot (`billedReason` key) when usage was settled, which is what a reload shows.
- moderation-ports/conversation | Generated images and moderation order. | Generated files are stored only after the output check passes, so a block never has stored output files to revoke on the live path; the output check receives the bytes (`ImageRef.Bytes`). A generated image without bytes is reported through `ReportOutputImageFailure` (failed-open, never a pass), only while the outcome is unsettled and the output-image scope has categories. Videos are not checked.
- moderation-ports/conversation | Temporary chat images. | `ModerationRequest.Images` carries the bytes of image attachments of the last message into the ephemeral input check; an empty-byte image is a failed-open event; nothing is stored.
- moderation-ports/engine | Image identity and evidence. | `ImageRef.SHA256` (the file record's stored hash) is the de-duplication key and the recorded hash; images without one are never duplicates of each other. The evidence copy is the prepared (downscaled) image with its encoded MIME and size, under `moderation-isolated/<event public id>/<index>_<first 16 hash chars>.bin`, `application/octet-stream`; the index is the image's position among the checked images, so an earlier isolation failure leaves a gap rather than renumbering.
- moderation-ports/engine | Recovery and cleanup corrections to the spec limits. | `worker_lost` events carry only the run id (no user, conversation or message ids) and make no stats increment; a remembered pending block suppresses the recovery notification; a failed late-block persistence sets the run back to `moderating` with the event id and categories; cleanup batches are 200 events x 50 passes, skip events whose image metadata cannot be parsed or that count images while no object store exists; blocked-file retries take 200; the fast pass has a 45 s and the full pass a 5 minute budget.
- moderation-ports/not-done | Spec scenarios not covered here. | Scenario 7 (single 21 MiB data URL alone) and 6 (batching) were already covered by the provider tests of the engine; 27 (extraction through `Materialize` on S3) has no consumer because the chat area extracts text in memory; the web client behavior of 4.5 and the `Materialize`-based extraction pipeline are outside the backend.

## admin-users

- admin-users/layout | No spec assigns the admin console routes to a new package, and the owners already hold the data. | No new area: the user area serves `/admin/users*` and `/admin/user-auth-events` (`admin_*.go`), the channel area serves `/admin/permission-groups*` and `/admin/models/{modelID}/permission-groups` (`groups_*.go`), the conversation area serves `/admin/conversation-events*` and `/admin/conversations/export` (`admin.go`). The registry is unchanged; the integration hub supplies the new ports (`internal/integration/admin_ports.go`). The older `integration/admin-area` line is superseded by this.
- admin-users/gate | Multi-user gating. | User and channel routes use `d.Gated(capability.MultiUser).Admin` (role check first, then 404 `feature.disabled` with details feature=multiUser); event and export routes are on the plain admin group.
- admin-users/user-ports | Subscription, balance and plan edits belong to billing. | `user.Ports.Billing` (Mode, Subscriptions, Accounts, AssignPlan) adapted from the billing service; `user.Ports.Audit` defaults to an `audit.Recorder` on the same database. The billing mode decides which half of the view is filled exactly as the spec says (self: subscription, usage: account, period: both).
- admin-users/user-view | The spec's view has billing account fields that the shared auth view hides. | `AdminUserView` embeds `UserView` and adds `billingAccountCurrency`, `billingBalanceNanousd`, `billingBalanceUSD`, `billingAccountStatus`; the additional auth-view fields (password flags, email source, onboarding) stay in the JSON since the spec allows unlisted fields. - admin-users/two-factor | The 2FA tables belong to the auth area. | `user.Accounts` reads and deletes `identity_mfa_settings` through a private row mapping (enabled flag, recovery-code count = length of the stored JSON array). When the table does not exist the reset route answers success without doing or auditing anything (the spec's "security component not available").
- admin-users/create-actor | Spec 2.2 lists 4.3 - 4.9 for the stored-role re-check; create (4.2) is not named. | Create also re-reads the acting user and requires a stored admin role (a demoted admin cannot create accounts).
- admin-users/empty-user-id | `user_id=` (present but blank) on the auth-event list. | Treated as absent; zero, negative, non-numeric and overflowing values are 400 `user.invalid_id`.
- admin-users/patch-order | The spec says the subscription and status steps persist before a later validation failure. | Steps 1 - 8 are validated first and written together at the end, so the only failure after an immediate write is an avatar the write-time check refuses (400 `user.invalid_avatar_url`, the allowed improvement). Role changes also revoke sessions after that write. The race-only 409 `user.last_superadmin_role_protected` from the atomic check is mapped but cannot be reached over HTTP (an acting superadmin implies a second superadmin), so it is covered by the account-level tests only.
- admin-users/audit-detail | Key names of the patch audit detail are open. | `avatar_url`, `display_name`, `email`, `phone`, `role`, `timezone`, `locale`, `profile_preferences`, `subscription_tier`, `subscription_expires_at`, `status` each as `{from,to}`, plus `email_verification_reset`, `phone_verification_reset`, `sessions_revoked`, `reason`. Import audit uses `source`, `dedupe_field` and the snake_case counters.
- admin-users/import-source | Source access details are open. | SQLite files are opened read-only through a `file:...?mode=ro` URI (a missing path fails with 500 instead of creating a database); `sqlite://` is stripped; PostgreSQL URLs are refused (400) in local mode. The source reads `"user"` (id cast to text, name, email) and, when a `credit` table exists, `credit.user_id`/`credit.credit`; a failing credit read is a 500. The fixed appearance JSON is `{"theme":"system","preset":"default","fontSize":"standard","font":"default","fontWeight":"default"}`.
- admin-users/import-username | The spec's collision order: 4-hex chunks, then an 11-hex window. | Chunks of the SHA-256 hex are tried from offset 0 in steps of 4 (the stem is cut to 11 characters so `stem-xxxx` fits 16), then `owui-` plus 11-hex windows sliding one character at a time, then a numeric suffix as a last resort that cannot be hit in practice.
- admin-users/import-key | `skippedInvalidRow` can only happen when both the source id and email are blank. | Since a blank email is already `skippedInvalidEmail`, the counter stays 0 in practice; it is kept for the documented order.
- admin-users/permission-groups | The channel area already had group maintenance with a different list order and counts. | Left in place for existing callers; the admin surface uses new `Admin*` methods (default group first then id, default group `manualUserCount`/`subscriptionUserCount` forced to 0 and `userCount` = all accounts, rule matching trims type/value and ignores empty values). `Options.Plans` (billing) and `Options.Verifier` (user accounts) are new optional ports; without a verifier the area reads `identity_users` itself.
- admin-users/permission-groups | Rule validation on PUT models. | A rule type outside `all|vendor|protocol|upstream`, or an empty value for the last three, is 400 `admin.invalid_permission_group_models`; `all` stores an empty value. A blank rule type passes body binding (non-empty) and fails here.
- admin-users/permission-groups | Plans referencing the group are checked outside the delete transaction. | The check and the delete are not atomic (SQLite keeps a single writer connection, so a cross-area read inside the transaction would deadlock); a plan bound in between is not detected.
- admin-users/conversation-events | `chat_run_events` has no message, conversation, user or latency columns. | Conversation, user and the five route fields come from a LEFT JOIN on `chat_runs.run_id`; the message id is the earliest assistant message carrying the run id (0 if none). Heavy bodies are only selected for the detail route; the list computes the payload size in SQL (`LENGTH(CAST(.. AS BLOB))` on SQLite, `OCTET_LENGTH` on PostgreSQL). `startedAt` falls back to `createdAt` when null.
- admin-users/conversation-events | User names for events. | Read from `identity_users` directly (live rows only; table absent means no names), like the error-log area.
- admin-users/export | The "export capability not configured" 500 cannot occur: the conversation area always has the export path. | Not implemented as a configurable port. The admin export audits first (`admin_export_conversations`, resource `conversation`, empty resource id), writes one line per live conversation of every user (id cursor, batches of 50), redacts blocked messages (user: placeholder content and `[]` attachments; assistant: empty content, `[]`, no trace/UI state, placeholder error message when empty; the event id comes from the message, else from its run), and an ownerless conversation exports with `runs: []`. ## ragindex

- ragindex | Where do the spec's endpoints live, given three areas already own routes (conversation: `POST /files/embeddings` and `GET /context-artifacts/{id}`; settings: the `/admin/settings/embedding/*` handlers behind the `EmbeddingIndex` port)? | The new area `ragindex` registers no routes. It exports a `Service` (submission, status, task list, reindex, retry, probe, reconcile, sweep, clone, forget, retrieval, turn planning) that the integrator hands to the settings area through `Service.WirePorts` (`Embedding`, `VectorStore`) and to the conversation area through the new `Ports.Indexer` and `Ports.Knowledge`. This supersedes the integration/retrieval line above ("not implemented").
- ragindex | The platform has neither pgvector, sqlite-vec nor a HNSW index (spec 5.3-5.5). | Vectors live in the plain table `file_chunk_embeddings` (chunk_id, user_id, file_obj_id, embedding_signature, dims, little-endian float32 blob) on both databases, as the memory area decided; search streams the rows of the permitted files and the current signature and ranks by exact cosine in Go. The availability check is "chunk, vector and file tables exist", remembered per process (a definite true or false is cached, errors are not). The spec's `file_chunk_vectors` virtual table and the 4096/4000-dimension rules are not created; vectors above 4096 dimensions are still rejected at publish.
- ragindex | `file_chunks` is declared by the conversation area (with `file_object_id`) and the spec names the owning column `file_obj_id`. | Both areas declare the same spec columns (`file_obj_id`, `user_id`, `chunk_index`, `page_num`, `char_offset`, `modality`, `content`, `token_count`, `embedding_signature`, `created_at`; no soft delete) so the idempotent migrations agree; the conversation model was changed accordingly and its file removal deletes by `file_obj_id`.
- ragindex | The index must read and write `file_objects`, which the chat-file store owns. | The area carries its own minimal `File` model (like the knowledge-base area) and writes only `embed_status`, `embed_signature`, `embed_error`, `chunk_count`, `updated_at` and, for administrator re-extraction, the processing and extract columns (`processing_*`, `extract_status`, `extract_text`). Any stored `embed_status` outside the six states (the store writes `disabled` at upload) means "never indexed".
- ragindex | The spec's "durable embedding queue" and "file-processing queue" have no platform primitive (the cache only offers key/value operations). | Table `file_embed_jobs` (kind `index` or `extract`, user, file, signature, host, attempts, delivered, available_at, lease_until) is the queue. Four workers poll it (every 2 s or when woken), take a job with a six minute lease (a job delivered before has `delivered > 0`, which makes the run a takeover), and delete it when settled. A new message replaces the pending one of the same kind for the file.
- ragindex | Retry rule for a failing message (spec: retried up to 3 times, file shows `queued` between attempts). | Attempts 1 and 2 put the file back to `queued` with the failure summary and reschedule with a 5 s x attempt delay; attempt 3 fails the file. Failures that cannot change on retry (no usable content, image too large or unsupported, protocol cannot embed the input, configuration changed, canceled) fail the file at once. A shutdown during a run gives the file and message back untouched.
- ragindex | How is "embedding unavailable at worker time" handled? | Configuration problems (disabled, model or host missing, signature or host differing from the message) mark the file `stale` ("configuration changed, resubmit") and settle the message; a missing provider client or vector store errors the message for retry.
- ragindex | Re-extraction (administrator retry, reindex) needs a text extraction service in the chat-file store, which only extracts text-like files at upload. | A `Content` port (`Text`, `Original`) supplies it; the integration reads the stored bytes through the chat-file facade and uses the configured Tika, Docling or MinerU engine, falling back to the built-in parsers (so PDF needs an external engine). The image-OCR switch and the PDF OCR fallback and page limit are not applied here. After extraction the file's `extract_text` and `extract_status` (`ready` or `empty`) are stored, `extract_chars`, `preview_text` and `page_count` are left alone.
- ragindex | `embeddable` (status and task lists: storage path plus file category) and `indexable` (submission and indexing: MIME or extension) are two predicates in the spec. | Categories are the union of the spec names and the chat-file store's (`pdf`, `word`, `presentation`, `excel`, `spreadsheet`, `text`, `document`, `code`; images by the OCR/pixel rule); `indexable` classifies by MIME and extension (text-like, PDF, Word, presentation, spreadsheet, image rule; video and audio never). The bulk rebuild applies both.
- ragindex | The reconciliation sentence ("queued, processing or ready without a chunk carrying the current signature becomes stale") would also stale a file that was queued a moment ago under the current signature. | Reconciliation stales `ready` files without a current-signature chunk and `queued`/`processing` files without one whose recorded signature differs from the current one; in-flight tasks of the current space are left alone. It also runs at start, after the stalled-task sweep.
- ragindex | Stall sweep and queue polling use which clock? | Row timestamps and age checks use the injected clock; the one-minute sweep ticker and the 2 s worker poll use real time. `Service.Sweep`, `Reconcile` and `DrainQueue` are callable directly (tests, tools). `Options.DisableWorkers` starts no worker.
- ragindex | Upload-triggered runs and `processing_status`. | An index run started after text processing moves `processing_status` to `embedding` and back to `ready`; a failure leaves processing `ready` with `processing_ready` true, `processing_error_code` `embed_failed` and the summary as the message. The sweep restores a stuck `embedding` the same way. Explicit (queued) submissions do not touch the processing status.
- ragindex | The text of `canVectorize` and `vectorizationReason`. | `canVectorize` is "an explicit submission would be accepted now"; `vectorizationReason` carries the skip reason or availability reason when not, and `outdated_index` (with `canVectorize` true) for `stale` files and `ready` files of another signature. Opt-out no longer blocks vectorization (only retrieval). The knowledge-base area's judgement loads the file by owner and public id (`Service.VectorizationOf`).
- ragindex | Image downscaling (spec 6.3) without a WebP decoder in the standard library. | JPEG, PNG and GIF are decoded, box-averaged to a long edge of 1536, 1024, 768 and re-encoded as JPEG (quality 85, over white); an image already within 4 MiB is sent as is; an oversized WebP cannot be shrunk and fails with "image too large".
- ragindex | Provider error classification (spec 6.4 summaries). | The integration wraps transport errors and non-200 answers in `ErrProviderUnavailable` ("embedding service unavailable"), keeps malformed answers (including a vector of the wrong width) as plain errors ("vectorization failed, retry later"), and maps the modality error to "protocol cannot embed this input type". Provider text, URLs and keys stay in the log only.
- ragindex | Keyword search in hybrid mode per dialect. | SQLite: every whitespace-separated term must occur as a case-insensitive substring (LIKE with wildcards escaped), ordered by chunk id, score 0.5. PostgreSQL: `ts_rank_cd` over `to_tsvector('simple', content)` with the tokens (each character above U+2E7F alone, ASCII letter/digit runs as words) joined by OR; this SQL is untested here (no PostgreSQL server in the build environment).
- ragindex | Retrieval cache key and the knowledge-base files' `updated_at`. | The key hashes cache version, user, collapsed query, endpoint, model, hybrid flag, top-k, minimum similarity, token budget, fetch multiplier, dimensions and each file's (object id, public id, chunk count, state, updated-at), sorted; entries live under `ragindex:retrieval:<sha256>`. The knowledge-base resolver does not return `updated_at`, so base files contribute id, chunk count and state only (a reindex that keeps the chunk count can serve a cached answer for up to the TTL).
- ragindex | Where is the chat-side retrieval plan (spec 8.2, 9.1, 10) implemented? | `ragindex.Service.PrepareTurn` takes facts (files with tokens and flags, resolved knowledge-base files, history, file mode, context-budget settings) and returns the dynamic-context block, per-file inline/retrieved decisions, images to attach, sources, evidence rows and the trace section; the conversation area gathers the facts (`knowledge.go`), applies the result and persists it. The context-token budget rule uses `chat.context_token_budget_enabled` and `chat.context_window_fallback_tokens`. - ragindex | Behavior when the conversation area has no `Knowledge` or `Indexer` port. | Unchanged from before: attachments are injected in full, selected knowledge bases are passed to the generator untouched, files are never offered for vectorization. The integration always supplies both.
- ragindex | Spec 8.2 says a disabled knowledge-base switch silently ignores selections, while the conversation spec rejects a send that names bases when the switch is off. | Both stay: the send is rejected at validation (400 `knowledge_base.invalid_reference`), and the retrieval step itself drops base ids when the switch is off.

Content is cut to 2000 characters in the stored row, the token estimate and hash cover the full text.
- ragindex | Reuse of earlier evidence (spec 10.4). | `historicalEvidence` (conversation) offers up to 4 recent artifacts of the active branch's assistant messages (kinds file_rag_chunk, file_rag_fallback, tool_result, native_tool_result, image_analysis, plus summary while no snapshot exists), newest first, snippets cut to 500 characters under a 600 token cap, as `<historical_evidence>` items appended to the dynamic context; evidence already in the current turn, other users' or expired rows and other branches are excluded.

- ragindex | Request validation of `POST /files/embeddings`. | The conversation handler binds 1 to 100 ids, each non-empty and at most 64 characters (`request.invalid_body`); whitespace-only ids pass, are dropped, and an all-blank request succeeds with empty lists without any availability check.
